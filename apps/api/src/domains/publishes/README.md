# Publishes with code

Publishing a draft with code puts its code and content on Live at the same moment, serving exactly the build members previewed (ADR 0020 and its amendments, spec #560 section 13). A draft without code publishes as before, in the request (`../drafts/publish.ts`).

`drafts.publish` takes the revision the review showed (`code.revision`). It refuses a revision that isn't the one the draft previews, or changes still building (`REVISION_CHANGED`). Otherwise it puts the draft in its publishing state (`drafts.publishing_revision_id`), starts the `camox-publish` Workflow (`workflow.ts`) and returns `{ publishing: true }` at once. The review shows "Publishing…" from the preview's `code.publishing`. Viewers learn the outcome through the project room: `draftEnded` when it lands, and a `drafts` invalidation, refreshing the review, when it goes back to it, with `code.publishAborted` saying why.

## Steps

A project's publishes with code run one at a time, in the order they were asked for, with an Upgrade ready to push to `main` (`queue.ts`): the drafts in their publishing state, the project's `publish_push_*` columns and its `upgrade_push_*` columns are the queue. The publish batch deletes the draft's row, so it sets `publish_push_*` in the same batch: the publish keeps its place until its push to `main` landed, and its squashed commit sits on the `main` its revision merged. Each publish waits for its turn, and wakes the next with a `publish-turn` event when it ends, however it ends. An Upgrade checks its turn every few seconds, and wakes the next publish once it pushed.

1. **The pinned revision must be the draft's head**, and the one it previews. A newer one goes back to the review (`revisionChanged`). A head whose build was pruned is built again in the draft's sandbox. When `main` moved and the draft hasn't merged it yet, the publish waits for its merge revision (`../revisions/merge.ts`), woken by a `draft-merged` event, and ships that: the head may be merges of `main` on top of the pinned revision, never an agent's revision. It ships once the draft previews the merge and it type checks. A merge that clashes or fails its type check goes back to the draft with the "doesn't merge with Live's" blocker (`codeDoesNotMerge`), as Camox's reconcile turn fixes it (`../revisions/reconcile.ts`); one that takes more than `MERGE_CHECKS` checks goes back to the review (`liveCodeMoved`).
2. **Upload without serving**: the revision's build, from its archive in `REVISION_BUILDS`, is the draft's own user Worker in the `production` dispatch namespace, its publish Worker, named `<Project ID>-publish-<draft ID>` and tagged `camox-publish-<Project ID>` (`scripts.ts`). The draft uploaded it ahead, as it previewed the revision (`DraftCode.prepareUpload`): the publish takes it, checks it's still there and holds the revision, and uploads it only if not (`DraftCode.uploadForPublish`). Nothing sends requests to it yet. It carries the variable `CAMOX_PUBLISHING_DRAFT=<draft>`. See "The publish's Worker" below.
3. **Re-check** Live's conflicts against the review's token, and blockers. Either goes back to the review, Live untouched.
4. **Promote** by pointing Live at the publish's Worker: `projects.live_script`, the project's live Worker pointer, names it, after the publish read the Worker it named before (null for the one named after the Project ID, which releases deploy). Dispatch reads the pointer through the API and keeps it for 2 seconds (`apps/dispatch/README.md`), so the publish then waits `LIVE_SCRIPT_SETTLES` before its batch: no request reads the new content with the previous code. Right before the promotion, the publish sets `drafts.publish_promoted_at`. From then until the batch commits, the publish's Worker's reads name the draft with `x-camox-publishing-draft`: the API reads them as Live overlaid with the draft, with no session, and as Live before the promotion or once the draft ended (`../drafts/access.ts`).
5. **The publish batch** (`publishWithCode`): the draft's content as any publish applies it, with the draft's definitions, which its previewed revision synced, replacing Live's. It aborts when the conflicts changed, or when the draft previews another revision. Then the pointer goes back to the previous Worker and the draft goes back to its review. Once it committed, its follow-ups (ending the draft's thread, deleting files no one uses anymore, requesting Live's generated values and merges) run as a unit of work of their own, so the draft's viewers hear `draftEnded` without waiting for them.
6. **Record the tree Live serves**: a succeeded `releases` row for this publish, so the next step's push releases nothing (`../releases/README.md`).
7. **Push one squashed commit to `main`**: the revision's tree, with the current `main` as its parent (`DraftCode.publishToMain`).
8. **Delete the draft's code**: its branch, R2 builds, working copy and sandbox (`deleteDraftCode`).
9. **Delete the previous publish's Worker**, if a publish's Worker served before: nothing rolls back to it anymore, and dispatch stopped sending requests to it before the batch.

A step that gives up puts the draft back to its review (`failed`). From the promotion until the batch commits, any failure, the promotion's own included, first points Live back at the previous Worker, retried until it lands (`UNTIL_DONE`), and waits `LIVE_SCRIPT_SETTLES`. A publish that doesn't land leaves the draft its Worker, for its next publish. The steps after the batch are retried until they land too: Live already has the draft's code and content, and a `main` left behind it would release old code over Live at its next push.

The publish never builds, except a pruned head (step 1), and never installs or runs `camox release`: agent-written code never runs beside the Deploy Token, nor beside Camox's `CF_TOKEN`.

## The publish's Worker

Workers for Platforms user Workers have no versions to upload without serving: gradual deployments aren't supported for them, every upload of a namespaced Worker serves at once, and wrangler's `versions upload`/`versions deploy`/`deployments status` don't take `--dispatch-namespace` ([limits](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/reference/limits/)). So each draft with code has a Worker of its own, and promoting or rolling back is moving the pointer, which dispatch reads (`apps/dispatch/src/live-script.ts`).

The draft uploads it ahead of its publish, which an upload would otherwise take most of (ADR 0020's last amendment). Each revision the draft previews (`../revisions/build.ts`) goes up over it at once, one upload at a time, and the review opening uploads the one it shows if that failed (`upload-ahead.ts`). Once a publish took the Worker, nothing replaces it until that publish ends. The draft's end deletes it, unless the draft published and Live serves it (`../code/drafts.ts`). The pointer stays on the publish's Worker until the project's next real release: a publish's push to `main` releases nothing, as Live serves its tree. Once a release deployed, it clears the pointer and deletes every publish's Worker by tag (`../releases/README.md`). The queue (`queue.ts`) keeps a release from doing so between a publish's promotion and its push to `main`: the pushes that release are Upgrades', queued with publishes, and drafts merge a push only once its release ended. Project deletion deletes them by tag too (`../project-deletion/README.md`).

The draft's `DraftCode` uploads it, with the Cloudflare API and Camox's `CF_TOKEN` (`src/lib/user-workers.ts`). Spec #560's Out of Scope listed "Calling the Workers versions API directly": this deviates from it, as wrangler can't upload a namespaced Worker without serving it (ADR 0020's last amendment). The upload follows Cloudflare's references:

- the assets upload session: `POST …/dispatch/namespaces/production/scripts/<name>/assets-upload-session` with the manifest (path → 32-hex-character hash of the base64 content and extension, and size), then every bucket of hashes it asks for, all at once, to `POST …/workers/assets/upload?base64=true`, as multipart parts named by hash, with the upload token; the one that completes the set answers the completion token ([Direct Uploads](https://developers.cloudflare.com/workers/static-assets/direct-upload/));
- the script: `PUT …/dispatch/namespaces/production/scripts/<name>`, multipart, with a `metadata` part and one part per module, typed `application/javascript+module` and so on ([Upload Workers for Platforms Script](https://developers.cloudflare.com/api/resources/workers_for_platforms/subresources/dispatch/subresources/namespaces/subresources/scripts/methods/update/), [multipart upload metadata](https://developers.cloudflare.com/workers/configuration/multipart-upload-metadata/));
- deletion: `DELETE …/scripts/<name>?force=true`, or `DELETE …/scripts?tags=camox-publish-<Project ID>:yes` for all of a project's ([tags](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/configuration/tags/)).

The archive is agent-built, so nothing of it runs and its `wrangler.json` is never trusted (`workerOfBuild`). The upload is made of:

- the server build's modules (`.js`/`.mjs`/`.cjs`/`.wasm`/text), from the directory of `dist/` beside `client/`: no source maps, `.dev.vars` or `wrangler.json`;
- its main module, compatibility date and compatibility flags, the only fields read from its `wrangler.json`: the main module must be one of its ES modules, the date a date, and the flags among the Template's (`nodejs_compat`). Anything else fails the publish;
- the platform's bindings only: the `CAMOX_PUBLISHING_DRAFT` variable. A release's Worker gets none from Camox either (the Template's `wrangler.jsonc` has none);
- the client assets of `dist/client/`, without what its `.assetsignore` names, with its `_headers` and `_redirects` as the assets' rules, as wrangler reads them;
- the `camox-publish-<Project ID>` tag.

## Upgrades

An Upgrade's push to `main` joins the project's queue (`../upgrades/project-workflow.ts`), so it never lands between a publish's promotion and its push to `main`, which would release `main` without the draft's code over Live, and the publish's squashed commit would then undo the Upgrade. Its push lands on the current `main`: it commits only `package.json` and the lockfile, after checking they're still those of the commit it built, which publishes never change. Publishes asked for after it wait for its push, then for their draft's merge of it. Drafts merge a push only once its release ended (`../releases/workflow.ts`), so a publish shipping the merge is promoted over the Upgrade's release, never under it.

## Tests

`workflow.integration.test.ts` drives publishes through `drafts.publish`, with the sandboxes and Artifacts faked at their bindings (`test/release-fakes.js`) and the Cloudflare API at its fetch (`test/fake-cloudflare-api.ts`). The fake revision sandbox archives a real gzipped `dist/`, whose `wrangler.json` asks for bindings and a build command a publish must ignore. The fake API keeps each project's user Workers with their metadata, modules and assets, records every call, and can fail, lose the answer of, or hold any call, per project. What serves a website is what dispatch asks the API.

## Cloudflare setup

- `wrangler deploy` creates the `camox-publish` Workflow and runs the `projects.live_script` migration. The Workflow calls the Cloudflare API with the API's `CF_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, which already have _Account › Workers Admin_ for releases' deploys (`../releases/README.md`). Nothing else to provision: no sandbox.
- Untested on real infrastructure: the upload itself (the assets session for a namespaced Worker, its metadata, tags on a namespaced upload), deleting by tag, and how fast dispatch's isolates pick up a moved pointer. A first publish of a test project should check that its Worker serves its assets with the build's `_headers`, that rolling back serves the previous Worker within seconds, and that the next release deletes the publish's Worker.
